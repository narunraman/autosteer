Tutorial

From browsing the questions to evaluating a model

Exploring the benchmarks

Each benchmark is a taxonomy. At the bottom are elements: economic concepts phrased as abilities to be tested, such as computing an expected utility. Related elements are grouped into modules, like the sections of an economics textbook, and modules into settings, like its chapters.

We have released two benchmarks, STEER and STEER-ME. Their pages let you browse the taxonomy down to single elements, where you can generate example questions. Take it for a spin with Law of Demand.

Questions and templates explains what a question is in more detail. To write a new set of questions of your own, run autoSTEER on your own machine.

Dynamic benchmarks

Benchmarks like MMLU are a fixed list of questions, and the list is the benchmark. STEER and STEER-ME are generators instead: every question is a template filled with fresh values, with its answer computed by code. So there are two ways to get questions:

DatasetsA frozen sample on Hugging Face: 20 questions for each type, domain and difficulty of every element. Everyone runs the same questions, so this is what to use for a score that others can compare with, as on a leaderboard{% if show_evals() %} like our Evals{% endif %}.
API or autoSTEERAs many fresh questions as you ask for, in any element, type, domain, difficulty and perspective, and the same seed gives the same questions. This is what to use for finding a model's weaknesses: more questions wherever it looks weak, and questions it cannot have seen in training.

The next two sections follow this split: scoring a model on the dataset, then finding where it fails with fresh questions.

Scoring a model

We provide steer-bench, which runs a model on the dataset and scores it. It is built on Inspect, so it works with API models and with open-weight models you run yourself. Install it, run a model, and make a report card:

uv tool install --with-executables-from inspect-ai git+https://github.com/narunraman/STEER
inspect eval steer_bench/steer_me --model openai/gpt-4o-mini -T element=law_of_demand --limit 50
steer-bench report logs/ --out card.html

The report card shows the model's accuracy, and its calibration where the model returns option probabilities, for every element, with averages by module and setting. Scoring explains the formats and metrics, and the steer-bench README covers the other options.

Note

To run a large open-weight model on a Slurm cluster, you can use slurm-llm. It serves the model with vLLM as an endpoint on your own machine, which steer-bench calls with --model-base-url.

Using your own harness

To run a model your own way, load the dataset:

from datasets import load_dataset
ds = load_dataset("narunraman/steer_me", "law_of_demand")

or draw fresh questions from the API:

curl "https://steer-benchmark.cs.ubc.ca/api/sample?element_name=law_of_demand&n=5&seed=42"

Every question comes with its answer. Scoring describes how we score them.

Finding where a model fails

A score is good for comparing models, but often what you want to know is where a model performs badly, especially on the questions that matter for your use. The report card helps: it breaks the score down by element, domain, difficulty and so on (see Diagnostics). But it works after the fact, and only shows the weaknesses the dataset has enough questions to reveal. A model might do well on medical questions and on hard questions, and still fail on hard medical ones, of which the dataset has only a few.

Because the benchmarks are dynamic, you can generate more questions for any such combination, but there are thousands of combinations. QuickScope decides which to test as it goes, spends questions where it is least sure, and reports the combinations where the model is reliably wrong, with a confidence bound. It runs on STEER-ME out of the box:

git clone https://github.com/narunraman/quickscope.git
cd quickscope && make sync
uv run qscope download steer_me
uv run qscope offline --scenario steer_me --utility error-rate --model gpt-5.4-nano
